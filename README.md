# 公交行驶轨迹整理（路段匹配）

把一辆公交车一次行程的定位点，整理成可用于路段运行时间分析的有向路段行驶轨迹。
提供 FastAPI + SQLite 网页：上传有向路段 CSV 与定位点 CSV、对路网修订发起几何质检、设置匹配半径、查看逐点归属与路段序列。
**路网质检通过是轨迹发布的前置闸门**（见下文“路网质检”）。

## 规则（与需求一一对应）

- 每个定位点只在**匹配半径内**的路段中取候选（点到有限线段的最短距离 ≤ 半径）。
- 相邻两点的路段只能：
  1. 保持同一路段；或
  2. 沿行驶方向进入下一段，且**上一段终点坐标 = 下一段起点坐标**（端点相接）。
- 在全程可连通的候选组合中，取**点到路段距离总和最小**者。
- 若不存在连通路径 → 待核，`reason=NO_CONNECTED_PATH`；
  若最小距离和对应**多条**路径 → 待核，`reason=AMBIGUOUS`；
  若某点半径内无路段 → 待核，`reason=NO_CANDIDATE`。
  三种情况都**不发布唯一轨迹**。
- 并列判定使用严格容差（绝对 1e-9 m + 相对 1e-12）；差在这个范围外即视为唯一。
- 端点相接的坐标比较按 1e-6 m 量化，避免浮点噪声。

## 路网质检（发布前置闸门）

路网上传后不能直接用于轨迹分析，必须先在网页对**当前路网修订**发起质检：

- 逐对检查同一平面层的路段：两路段**至少一方的内点相交**（未拆分交点 / T 字接入），或**共线且有正长度重叠区间**，即判缺陷，标出路段号、交点坐标或重叠区间（含长度）；
- 仅在双方**端点相接且无重叠**时视为正常，端点比较按 1e-6 m 容差，共线/平行按 1e-9 级严格容差，重叠长度须大于 1e-9 m；
- 质检**发起即停止供数**：该修订当前结果立即失效（`NETWORK_QC_OPEN`），匹配任务作废，页面不再提供任何轨迹；
- 检出缺陷 → **质检不通过**（`rejected`），缺陷清单逐条展示，该版路网不得放行轨迹，需更正路网后重新上传；
- 计算出错或进程中断 → 维持**待核**（回到 `pending`，指数退避，可在网页重试；重启自动重置 `running` 质检）；
- 质检**通过**后才安排该版轨迹重算。只有“路网质检通过 + 定位点修订现行 + 半径现行”三者同时成立，匹配任务才可被领取、结果才可发布（领取与发布两处都有闸门，防止过期结论放行）；
- **上传新路网立即撤销旧质检**（旧记录置 `revoked`）；质检、匹配与更正交错时，换版、重开质检、改半径都会让在途结论作废，绝不凭过期结论放行轨迹。

## 修订与失效

- 路网、定位点各自维护递增修订号（r1、r2 …），每次上传是**整版替换**并立即成为当前版本；历史修订保留供追溯。
- 新版受理的同一事务里，依赖旧版的所有已发布结果被标记失效（`NETWORK_REPLACED` / `POINTS_REPLACED`），页面单独列出且标注“不得用于路段运行时间分析”。
- 改半径（`RADIUS_CHANGED`）同样使旧结果失效并安排重算。
- 重算任务的发布动作会再次核对“路网修订 / 定位点修订 / 半径”是否仍为当前值；不一致则任务作废（`SOURCE_CHANGED_DURING_RECOMPUTE`），绝不发布旧结果。
- 计算失败的任务回到 `pending` 并有指数退避重试；进程重启时把遗留的 `running` 任务重置为 `pending`，因此失败或重启后仍处于待重算状态，不会丢失。

## 本地运行

```bash
python3 -m pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
# 打开 http://localhost:8000
```

数据库默认在 `./data/track_matcher.sqlite3`，可用 `TRACK_MATCHER_DB` 覆盖。
`TRACK_MATCHER_WORKER=0` 只关闭后台计算线程（测试用）。

## Docker Compose

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据保存在命名卷 `track_matcher_data`。容器内为单进程（后台计算线程与 Web 在同一进程），SQLite 文件位于卷上。

## 自测

```bash
python3 -m pytest -q
```

测试覆盖：平行路段择优、精确并列的歧义、反向/跳段不可连通、半径边界、以及“定位点更正 → 旧结果失效 → 重算 → 路网更正 → 再重算”的交错流程。

## 示例文件

`sample/` 下：

- `network.csv` + `points.csv`：两条平行路段，点更靠近北侧，质检通过后应发布唯一轨迹 `N101 → N102 → N301`。
- `network_parallel.csv` + `points_parallel.csv`：两条互不相接的平行路，恰好形成并列最优 → 待核。
- `network_defective.csv`：含未拆分交点（X1 横穿 N101/N201）与共线重叠（X2 压在 N101 上），质检应不通过并列出 5 处缺陷，用于手工验证质检页面。

## 验证状态

已在本机（Python 3.11）实际执行：

- `python3 -m pytest -q` → **75 passed**：匹配算法、网格索引对拍、质检几何边界（端点相接、T 字接入、十字相交、共线重叠/反向重叠/完全包含/重复、浮点噪声、平行与相离）、质检状态机与闸门、版本/失效/任务状态、HTTP 端到端、后台线程（含质检与匹配的失败重试、重启重置）。
- `uvicorn app.main:app` 实际启动并用 `curl` 走完整流程：上传样例 → 未质检时任务不可领取、页面显示闸门 → 发起质检后旧轨迹立即停止供数 → 质检通过自动重算并发布 `N101 → N102 → N301`；上传 `network_defective.csv` 后质检不通过、列出 5 处缺陷且无轨迹发布；再上传正确路网并手工把质检与任务置为 `running` 后重启进程，日志出现 `reset ... interrupted job(s)` 与 `reset ... interrupted quality check(s)`，过期质检正确撤销、新质检通过后轨迹重新发布；重开已通过的质检会立即失效现有结果，再次通过后重新发布。
- `docker-compose.yml` 仅做了结构校验；**本环境没有 docker 命令，未实际构建镜像或 `docker compose up`**，因此容器启动通路属于未验证项。
- 单进程内使用后台线程计算（质检优先于匹配领取），未做多副本/多 worker 水平扩展；大文件目前是全量读入内存解析（上传上限默认 20 MB）；质检为 O(n²) 路段对检查（带包围盒过滤），超大路网需关注耗时。
